## 1. 核心架构设计阶段（第1-2周）

### 1.1 技术方案选型分析
- **方案A：DXVK/VKD3D 移植层** — 翻译层，兼容性好但有性能损耗
- **方案B：原生 Vulkan 后端重写** — 完全重写渲染器，性能最优但工作量巨大
- **方案C：混合方案** — 核心渲染管线用原生 Vulkan，特效/后处理用翻译层
- **推荐**：方案C，分阶段实施

#### ✅ 决策（2026-10-03，PoC 实测后定案：**方案C，分阶段 + 可降级**）

首周行动项 #6「基于 PoC 测试结果决定全原生还是混合」的结论。**依据全部来自本仓实测**
（`docs/01` §7.6–§7.9），不是纸面推断：

| # | 实测证据 | 对选型的意义 |
|---|---|---|
| 1 | Present 拦截七通道在**双环境**（renderdoc 包装类 / 真 dxgi 类）走通，且方案B 函数层 detour 可独立承担（`经 函数detour` 3001 次、60 FPS） | **入口风险清零**：无论选哪条路，拦截面都成立，且有 vtable 层 + 函数层双保险互为兜底 |
| 2 | PoC-B 在 D3D11 进程内创建 **Vulkan instance/device（apiVer 1.4、GPU LUID 与 D3D11 一致）**，与 d3d11/dxgi、RenderDoc 包装层、GFE 覆盖层共处 4200 帧零失败 | **"混合"不是假设**：两套 API 同进程、同 GPU 互认稳定 → 方案C 的前提成立 |
| 3 | 刻意**不开 Vulkan swapchain**（与游戏/RenderDoc/GFE 抢 HWND ⇒ 结果不可判）→ 改离屏渲染 + 像素落 D3D11 backbuffer 才拿到可验收结果 | **呈现主权是硬约束**：混合方案必须是"合成式"——游戏照常 Present、我在 Present 链内驱动 Vulkan 渲染并合成进 backbuffer；另开 swapchain 属于未验证的高风险项，单独立门槛 |
| 4 | 注入路径均值 **6.47 ms/帧**——这是 `vkCmdCopyImageToBuffer` 读回 + host→`UpdateSubresource` 的同步代价（PoC 为"可验证性"买单） | **性能教训直接转化为架构约束**：生产通路**禁止每帧同步读回**，必须走 D3D11↔Vulkan 共享纹理（NT handle + fence）；该通路列为阶段1 实施项并单独测量 |
| 5 | `community-shaders/dxvk` = CS 自己维护的 DXVK fork（`docs/01` §1/§2） | 翻译层路线有活教材，**降级路径随时可用**，不是单行道 |

**阶段划分与门槛（每阶段 exit criteria，不达标即降级）**：

1. **阶段0（✅ 已完成）**：入口 + 共存证明 = PoC-A / PoC-B 双环闭合。
2. **阶段1 配对验证**（`docs/03` §7.1 第②条）：Vulkan 侧产出候选帧 → 同套提取链 + `rdc_compare`
   10 锚点全绿；同时把数据通路换成共享纹理（读回路径不得带进本阶段结论）。**水体顺位 1**
   （先探针升质，SSR 第二步，`docs/03` §7.2）。
   > **标定注记（2026-10-03）**：「10 锚点全绿」按分级口径执行 = A 类逐帧确定锚点全绿 + F 类注入
   > 指纹必现 + B 类会话敏感项按 `docs/02` §12.6 看图归因（字面 10/10 仅同帧自比成立）；
   > 水体场景双帧标定 S4b/S4c 已在档（指纹三口径全中 + 噪声底实测），见 `docs/02` §13。
3. **阶段2 核心管线逐 pass 原生化**：水体 → 天空 → 材质（`docs/03` §8 顺序），每 pass 门槛 =
   锚点全绿 + 本机 1920×1080 / GTX 1660 Ti 上帧时**不劣于基线 5%**（S4、S5 各测）。
4. **阶段3 特效/后处理**：按阶段2 实测数据决定原生实现还是保留翻译层。

**降级判据**：阶段1 锚点无法全绿、或阶段2 任一 pass 连续两次迭代既不过锚点也不达标 → 回退
**方案A（DXVK 路线，参考 CS 的 dxvk fork）**；此时阶段0 的拦截面与阶段1 的配对 harness 照常可用，
沉没成本仅限已写的 pass 代码。

**诚实边界（PoC 没证明的事）**：① 没证明能原生接管整帧呈现；② 没证明共享纹理通路的性能
（读回 6.47 ms 不代表共享通路的成本）；③ 没评估 ENB/ReShade 共存（风险项 #3）；
④ 没覆盖全屏独占/分辨率切换路径。

### 1.2 渲染架构抽象层设计
```
Renderer Interface (抽象层)
├── Device Management (设备管理)
├── Resource Management (资源管理: Buffer, Texture, Sampler)
├── Pipeline Management (管线管理: Graphics, Compute, RayTracing)
├── Command Buffer Recording (命令缓冲录制)
├── Synchronization (同步原语: Fence, Semaphore, Event)
├── Descriptor Management (描述符集管理)
├── Memory Allocation (内存分配策略)
└── Debug/Validation (调试验证层)
```

### 1.3 Skyrim SE 渲染管线逆向分析（关键）
需要通过以下手段分析：
- **RenderDoc / Nsight Graphics** 抓帧分析
- **x64dbg / IDA Pro** 静态分析渲染相关代码
- **Skyrim SE Creation Kit** 研究渲染资源格式
- **ENB / ReShade 源码** 了解现有注入点

**关键渲染阶段识别：**
1. Shadow Map 渲染（级联阴影 / 点光源阴影）
2. G-Buffer Pass（延迟渲染几何阶段）
3. Lighting Pass（延迟光照 / 前向光照）
4. Volumetric Lighting / God Rays（体积光）
5. SSAO / SSDO（环境光遮蔽）
6. Transparent / Alpha Pass（透明物体渲染）
7. Water Rendering（水面渲染 — 反射 / 折射 / 流动）
8. Particle System（粒子系统）
9. Post Process Chain（Bloom, Tonemap, AA, Motion Blur, DOF）
10. UI Overlay（Scaleform / GFx UI 渲染）

### 6.5 帧时间感知调度（脚本让位渲染）

**背景**：CPU 同时参与脚本（Papyrus）、游戏逻辑与渲染提交，脚本过多时会拖延渲染提交导致卡顿。
目标：帧时间超标时**优先保障渲染**，富余时再跑脚本。

**关键认知（设计前提）**：
- GPU 渲染是异步的，CPU 只做命令提交。**不能**等 GPU 画完再跑脚本（会串行化），正确做法是
  让提交不被脚本拖延 + 把脚本塞进 GPU 干活的空闲窗口（CPU/GPU 重叠）
- 引擎已有原生机制：Papyrus 预算制时间片（`fUpdateBudgetMS`，超预算纤维自动挂起顺延），
  即"渲染优先、脚本延后"的骨架已存在，本项工作是**让它变智能**，而非发明新机制

**实施方案（按侵入度排序）**：
- [ ] **方案 A（推荐）动态帧预算**：Hook 主循环/Present 处测量 CPU/GPU 帧时间，
  超标帧压缩脚本预算（6ms→1ms 或 0），富余帧还原/放大预算
- [ ] **方案 B（进阶）脚本移入 GPU 忙碌窗口**：把脚本时间片从"渲染提交前"挪到
  "Present 之后、下一帧提交前"（此时 GPU 正在画上一帧，CPU 空闲）——主循环流水线重排
- [ ] 方案 C（不做）：Papyrus 挪独立线程 — VM 非线程安全且脚本读写主线程游戏对象，会数据竞争/坏档

**脚本兼容性风险评估**：
| 场景 | 影响 |
|---|---|
| 偶尔顺延 1-3 帧 | ✅ 无影响（引擎原生设计如此，脚本必须容忍） |
| `Utility.Wait()` 类计时 | ✅ 基本无影响（挂钟时间，不依赖帧数） |
| 长期高负载下预算压缩 | ⚠️ 脚本延迟累积，战斗时法术/任务逻辑感觉变慢 |
| "每帧必须执行"的写法 | ⚠️ 边缘风险（不良写法但存在此类 mod） |
| 终止/跳过执行中的脚本 | ❌ 禁止 — 只能挂起不能终止，否则状态机损坏 |
| 脚本挪线程 | ❌ 禁止 — 数据竞争、存档损坏 |

**卡顿根因排查顺序（先治本再调调度）**：
1. 驱动着色器编译（首次遇到新材质）→ 本项目用**管线预编译/后台编译**根治（见 3.4）
2. 同步资源加载（贴图上传阻塞主线程）→ **异步上传队列 + 拷贝队列**根治
3. Papyrus 预算超支 → 本节方案 A/B
4. Havok 物理 / 动画任务尖峰
5. 显存/内存分配、驱动问题

**依赖**：GPU Timestamp Query 测量管线（与 5.5 性能分析叠加层共用）、主循环 Hook（见 5.2）
