**实测数据**（`docs/analysis/S4-extract-pass5.json` → `draw_segments` start=39270）：

| rt0 | `ResourceId::585`，**1920×1080 R16G16B16A16_FLOAT**（16 次全程相同） |
| dsv | `ResourceId::461`，**1920×1080 D24S8_TYPELESS**（16 次全程相同） |
| **viewports** | **1920x1080 = 16** ← 16 次**全部**全屏 |
| **scissors** | **off = 16** ← 16 次**全部**关闭裁剪 |
| PS | 15478×1 / 15990×4 / 17352×11 |

**相邻段对照**：

```
ev39215        1 draw   → rt0=321, dsv=0（无深度）, PS 17557
ev39270-39502  16 draw  → rt0=585, dsv=461, PS 15478/15990/17352   ← 段16
ev39530        1 draw   → rt0=321 + RT1=591, dsv=461, PS 17586     ← 段17 并回
ev39585-43994  242 draw → MRT×3 [321,583,337]                      ← 段18 透明/水
```

**三个推论**：

1. **不是分块** —— 16 次都用满1920×1080 viewport 且 scissors 全关，排除 4×4 分块假设
2. **是 16 层全屏叠加** —— 同一 RT0、无 ping-pong ⇒ 必然靠 **blend 合成**（否则最后一个覆盖前 15 个，只有 1 个可见，不合理）
3. **⇒ 整体抑制 16 个 = 丢掉 PS 15478 与 PS 15990 的全部贡献**，不只是丢反射

**修复方法**：

1. `docs/05` D3b 行改为：
   > 「b：抑制式 —— **不是整体抑制 16 个 draw**。实测（`S4-extract-pass5.json` seg39270-39502）：16 次 draw 全部 1920×1080 viewport、scissors 全 off、rt0 恒为 585、dsv 恒为 461，PS 分布 15478×1 / 15990×4 / 17352×11 ⇒ **同一 RT0 无 ping-pong，必为 blend 分层合成**。因此只替换其中**反射那一份**：候选 = PS 17352 组（11 个，唯一声明 `dcl_resource_texturecube t3`）或 PS 15478（1 个）。**准入前置 = 三个 PS 的反汇编 + blend/depth-stencil state（当前缺失，见 D-1/D-2）。**」

## ✅ C-1 `logLine` 每行开关文件 + 污染帧时基线（**v0.18.1 已修**）

**位置**：`src/poc-presenter/main.cpp:531-541`

```cpp
void logLine(const std::string& msg)
{
    const std::string line = "[" + timestamp() + "] " + msg + "\r\n";
    OutputDebugStringA(line.c_str());
    if (!g_logPath.empty())
    {
        std::ofstream f(g_logPath, std::ios::app);   // ← 每行一次 open + 析构
        if (f)
            f << line;
    }
}
```

**修复方法**：

```cpp
static FILE* g_logFp = nullptr;

void logLine(const std::string& msg)
{
    const std::string line = "[" + timestamp() + "] " + msg + "\r\n";
    OutputDebugStringA(line.c_str());
    if (!g_logPath.empty())
    {
        if (!g_logFp)
        {
            g_logFp = fopen(g_logPath.c_str(), "ab");
            if (g_logFp)
                setvbuf(g_logFp, nullptr, _IOFBF, 64 * 1024);   // 常驻缓冲
        }
        if (g_logFp)
        {
            fwrite(line.data(), 1, line.size(), g_logFp);
            fflush(g_logFp);          // 1 次 write syscall，替代 open+write+close
        }
    }
}
```

配套：`DllMain` detach 时 `if (g_logFp) { fflush(g_logFp); fclose(g_logFp); }`。

**效果**：每行成本从「open + 分配缓冲 + write + close + 析构」降到「1 次 fwrite」。
**同时消除 P0-6 的基线污染源。**

## ✅ C-2 2b 与 2d 的 desc 预检逻辑完全重复两遍（**v0.18.1 已修 → `copyResDescChecked`**）

**位置**：`main.cpp:1982-2004`（2b 哨兵）与 `main.cpp:2017-2053`（2d 出向）
`dsc` lambda 两处逐字相同；`ssrResObj` 预检 + 比较 + `[desc一致]` 分支也同构。

**风险**：已踩过「`CopyResource` 返回 void、desc 不一致时静默丢弃但日志照打」的坑。
**两处独立演进，其中一处改了另一处没改 → 判读口径分叉。**

**修复方法**：抽成共用函数

```cpp
// dst <- src 的 CopyResource；先比 desc 再拷，统一打 [desc一致] / [desc不一致!]
static bool copyResDescChecked(ID3D11DeviceContext* ctx,
                               ID3D11Resource* dst, ID3D11Resource* src,
                               const char* tag, unsigned long long k)
{
    D3D11_TEXTURE2D_DESC sd{}, dd{};
    void *so = nullptr, *dso = nullptr;
    const bool sok = ssrResObj(src, &sd, &so);
    const bool dok = ssrResObj(dst, &dd, &dso);
    const bool same = sok && dok && descEqual(sd, dd);
    g_ssrSelfCopy = true;
    ctx->CopyResource(dst, src);
    g_ssrSelfCopy = false;
    if (k <= 8 || (k % 128) == 0)
        logLine(std::string("SSR侦察: [") + tag + "] #" + std::to_string(k) +
                (same ? " [desc一致]"
                      : " [desc不一致!] dst=" + descStr(dd) + " src=" + descStr(sd)));
    return same;
}
```

2b / 2d 各调一次。**顺带把 2c/2d 两份 FNV 自校验驱动逻辑也合并。**

## ✅ C-7 `[2d] 出向读回` 节流计数只在打日志分支推进 —— 「每 600 次采一次」从未发生（**v0.18.2 已修**）

**位置**：`src/poc-presenter/main.cpp:2086-2090`（2026-10-06 `v0.18.1` 回归时顺带查出）

```cpp
const long cc = g_ssrOutChkN + 1;
if ((g_ssrOutStg && g_ssrInStgC && g_ssrInTexC) &&
    ((cc <= 3) || (cc % 600) == 0))
{
    g_ssrOutChkN = cc;      // ← 只有"该打日志"的分支才推进计数
    ...读回 + logLine...
}
```

**现象**：两轮实跑（`v0.18.0` 172597 次回写、`v0.18.1` 4024 次回写）`[2d] 出向读回` **都恰好只有 3 行**

**不推进** → `cc` 永远停在 4 → **`cc % 600` 永不命中**，第 4 次及以后一次都没采过。

**对照（正确的写法就在同一个文件里）**：2c 的 `ssrInQueue` 是

```cpp
const long c = ++g_ssrInLogN;              // ← 进门先推进, 每次事件都算一次
```

**修法（归 v0.18.2，与 2d-3 同批）—— 已落盘 `main.cpp`（2d 块内，原文原位替换，正文不变）**：

```cpp
// C-7: 计数**进门先推进** (同 2c 的 `++g_ssrInLogN`)。...
const long cc = ++g_ssrOutChkN;            // ← 每次回写事件都算一次, 不管 staging 闸在不在
if ((g_ssrOutStg && g_ssrInStgC && g_ssrInTexC) && ((cc <= 3) || (cc % 600) == 0))
{
    ...读回 + logLine...                    // ← 原 `g_ssrOutChkN = cc;` 已删
}
```

写成**扁平版**（`++` 提到 staging 判定之外、两条件合并）而非文档原案的嵌套版，理由：
① 正文零改动、只动计数行与删一行，风险面最小；
② 语义与 2c 完全一致 —— 2c 的 `++g_ssrInLogN` 也是**进门先推进**、staging 闸只管「这一次
采不采」，计数照样累加（否则 staging 尚未建好时的事件被漏计，`cc` 就又对不上事件序号了）。

  ① 头 3 行**全一致**，且这 3 帧恰好**每帧都有阻塞读回**（`2c#1~#3` + `2d#1~#3` 连着跑，`Map` 会把

  帧时基线反而略好（末窗 CPU/GPU **16.75/16.68** vs v0.18.2 的 16.84/16.89，`>20ms` 4 → 2）
  ⇒ `Flush` **零代价、予以保留**；但「只提交不等 GPU」在零跨 API 栅栏下**仍构不成顺序保证**
